## Core logic

1. **Planning date:** 2026-03-16.
2. Parse `inventory_breakup` and `open_po_details` JSON.
3. Treat `orderedquantity` as the dataset's aggregate open-PO units. The JSON detail is parsed and retained for reconciliation, but it is not assumed complete for every row.
4. Target inventory = (`inv_norm` + `safety_stock`) × `max_drr`.
5. Required new units = max(target inventory − current on-hand − open-PO units, 0).
6. Round the required order **up to whole `case_size` multiples**.
7. Enforce the required **space cap** by limiting the suggested quantity to the largest whole-case quantity ≤ `max_allocated_space`.
8. Enforce MOV:
   - `VALUE`: order value (units × CP) must meet `current_vendor_mov`.
   - `CASES`: order cases must meet `current_vendor_mov` (the MOV field is read as a case-count threshold under this criterion — see Assumptions).
   - `TONNAGE`: supported defensively as order tonnage ≥ MOV.
9. **If the case-rounded order needed to satisfy inventory norms is below the vendor's MOV, the order is raised to the minimum number of cases that meets MOV, bounded by the space cap.** If MOV still can't be reached within the space cap, the planner places the *maximum feasible* whole-case order (not just the smaller inventory-norm figure) and flags `MOV_NOT_MET_SPACE_LIMIT`. If no replenishment is needed at all (`required_cases == 0`), no order is forced purely to hit MOV, and the row is flagged `NOT_REQUIRED`.
10. Current DOI = on-hand / DRR when DRR > 0. Stored in `replenishment_audit.csv` (`current_doi`) and computed directly in SQL Query 2, since it is not one of the six required Python output columns.
11. Projected DOI = (on-hand + open PO + suggested order) / DRR when DRR > 0.
12. Zero-demand SKUs receive no replenishment; DOI is blank where DRR is zero.

## Key assumptions

- **`orderedquantity` is authoritative for the open-PO pipeline**, over the (sometimes incomplete) `open_po_details` JSON — see "Why open POs are handled this way" below.
- **`minimum_order_criteria == "CASES"` treats `current_vendor_mov` as a case-count threshold**, not a monetary value, even though the column is generally described as an order value. This was the most workable reading given the field is reused across both criteria.
- **The suggested order is raised to meet MOV whenever space allows, and maximized to the space cap when MOV can't be fully met.** An order that doesn't reach the vendor's minimum isn't a placeable PO, so under-shooting MOV (or leaving usable space unused) would produce suggestions that don't reflect what could actually be ordered.
- The six output columns (`final_suggestion`, `final_cases_suggestion`, `final_value`, `final_days_of_inventory`, `final_tonnage`, `mov_check`) already exist as blank columns in the source `assignment_data.csv` per the 36-column schema; the script overwrites them in place rather than appending duplicate-named columns (a bug in an earlier version of this script caused a `sqlite3.OperationalError: duplicate column name` when writing `replenishment.db` — fixed by dropping the placeholder columns before merging computed values).

## Why open POs are handled this way

The assignment explicitly provides `orderedquantity` as the total units already on order and asks the planner to account for open POs in the pipeline. Therefore all currently open PO units are deducted before calculating the new requirement. The JSON is parsed because the assignment explicitly requires JSON handling, but the aggregate `orderedquantity` is used as the authoritative pipeline total where the detail JSON is incomplete.

## SQL

`replenishment_queries.sql` contains:

1. **Vendor-level summary:** total suggested value, cases, units, SKU count, projected DOI and MOV exceptions.
2. **Top 10 riskiest SKUs:** lowest current DOI where `max_drr > 0`, including facility, vendor, title and current DOI.
3. Bonus sales-band inventory-health summary.

The schema is a single flat table (per the assignment's starter schema), so these queries use `GROUP BY`/aggregation rather than joins — there is no second table to join against.
